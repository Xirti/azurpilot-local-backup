## 大世界当前最值得处理的链条

45 秒误报修复的四个文件哈希仍匹配，所读两日日志未匹配到相应报错；这支持保留修复，不能证明所有海域都已实机通过。10-10 仍有 491 条 NemuIpc 调用超时警告。单条 warning 有自动重试，只有 CRITICAL 的 screenshot() 重试失败才说明该轮取图耗尽。10-09 有多轮耗尽及 EmulatorNotRunningError，不能只靠延长自律寻敌时间掩盖。

最新原配置：每月开荒和侵蚀1 Scheduler.Enable=false，但**智能调度 Enable=true**，三个 Sensitive 均为 false。`module/os/tasks/scheduling.py::_run_scheduled_hazard1_leveling()` 会直接代理执行侵蚀1逻辑，所以单关侵蚀1的独立 Scheduler 并不能保证侵蚀1不再执行。复核大世界时先同时暂停“智能调度”“每月开荒”“侵蚀1练级”，开启对应“敏感任务”，保留全局“敏感任务出错时禁止重启”。本轮在独立本地版这样设置；原安装任务开关没有替用户修改。

取图 / 控制稳定后，先在普通页面做短检查，再单独做一次海域完成 → 切海域检查。只改变一个变量：先关闭远程和多余网页 / 视频；再尝试 MuMu 3 GiB 与 4 GiB；截图超时仍持续时试 ADB 截图。保存改变前后的时间段和原始截图，比较单位时间的 timeout 与耗尽次数。不要把 CPU/内存压力当成已经证明的唯一根因。

## 更新究竟覆盖什么

旧日志中确有 WebUI 更新执行 `git reset --hard origin/master` 的记录，它会覆盖已跟踪的修复源码。实际 `config/alas2.json` 与 `config/deploy.yaml` 在原仓库被 Git 忽略；不能据此宣称它们一定被 reset --hard 擦掉。当前 ConfigUpdater 的内存夹具验证也保留三项任务的 Sensitive=true/Enable=false。

配置迁移仍可能对隐藏/锁定字段、无效枚举、旧任务键和已不支持活动应用默认值，活动默认关卡还存在 D3 规则；安装器/重新建实例/用户操作也可能重建配置。尚未找到最近三个 Sensitive=false 的唯一写入者。采用“更新前私人备份 + 新版迁移 + 逐项恢复 + 启动前校验”来覆盖这些情况，不为未证实原因编造修复。
